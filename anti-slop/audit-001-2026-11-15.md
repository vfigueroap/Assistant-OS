# Auditoría y verificación de Personal OS

Fecha: 15 de noviembre de 2026, America/Santiago. Alcance: aplicación propia, arranque, contratos, migraciones locales, adaptación del gimnasio y estructura del proyecto. El código completo de openGym se conserva como dependencia upstream, sin prometer una auditoría de todos sus controles.

El usuario autorizó revisar y corregir antes, durante y después, sin preguntas. Se aplicaron Ponytail full, Karpathy y antislop. El aspecto del portal se declara **borrador sin dirección visual confirmada**, con ENERGY 1 / RHYTHM 1 / MOTION 1; las decisiones y sus motivos están en `DESIGN.md`.

Resultado del Delivery Gate en el alcance indicado: **PASS**. Verificación final: 27 pruebas unitarias/SQL, 7 de transporte, 2 de extracción y 11 de navegador aprobadas; ambos builds comprobados. El navegador se probó sobre la versión compilada, con las limitaciones de servicios reales descritas al final.

## Hallazgos iniciales y correcciones

1. **Alta, R-35:** `npm run check` fallaba porque faltaba `apps/web/src/main.tsx`. Se implementó el portal y se comprobó con build y navegador.
2. **Alta, R-26:** `dev:api` y `setup` apuntaban a archivos ausentes; el gimnasio carecía de sus endpoints. Se implementaron los contratos que ya consumía el adaptador, sin crear otra API de registros.
3. **Alta, R-27/R-35:** no había estados comprobables ni recorridos de navegador del portal. Ahora existen vacío, carga y error, incluidos JSON dañado, almacenamiento lleno y fallo de conexión.
4. **Alta, R-36/R-38:** el límite real de la base no coincidía con los snapshots anunciados por el transporte. La migración nueva admite 8 MiB y partes base64 de 349528 caracteres, con pruebas SQL del límite exacto.
5. **Alta, C-2:** una colisión entre variable y alias impedía aplicar la migración original en una instalación nueva. Se corrigió el alias y se ejecutaron ambas migraciones en PostgreSQL embebido.
6. **Alta, C-4:** una pestaña podía sobrescribir registros locales de otra; los archivados en nube quedaban fuera de cargas posteriores. Se añadieron Web Locks, combinación sobre el último estado, comprobación de revisión, eventos de almacenamiento, carga de archivados y pruebas de concurrencia.
7. **Media, C-1/C-3:** había dependencias propias sin uso y dos copias generadas del gimnasio. Se retiraron Eve, router, iconos, tipos de Vercel y tsx; se conservó PGlite porque prueba SQL/RLS. El build del gimnasio apunta directamente a `dist/gym`.
8. **Alta, C-2/C-4:** categorías con nombres heredados corrompían totales; el planificador descartaba disponibilidad útil; fragmentos largos excedían el contrato del worker. Se corrigieron los casos en el código compartido con pruebas de regresión.
9. **Alta, R-38:** el límite de confianza del transporte gym se comprobaba después del staging. Ahora una URL externa se rechaza antes de enviar sesión o partes; la prueba cubre también un estado grande.

## Evidencia de funcionamiento

- TypeScript y pruebas Vitest: 27 pruebas aprobadas, incluidas API, worker, dominio, persistencia local y migraciones.
- Transporte gym: 7 pruebas Node aprobadas, con chunks, CAS, SHA256, fallo intermedio, merge offline y aislamiento del service worker.
- Extractor: 2 pruebas Python aprobadas, con fragmentos de 30000 caracteres y avisos OCR consolidados.
- Navegador: seis pruebas locales, cuatro de nube simulada y una del gimnasio compilado en Microsoft Edge. La simulación bloquea solicitudes externas no previstas.
- Instalación de dependencias: lockfile sincronizado, `npm ls --depth=0` sin dependencias incumplidas. La poda retiró paquetes ajenos a las importaciones propias.
- Build completo aprobado. Salidas independientes `dist/web` y `dist/gym`: recompilar el portal conserva los medios del gimnasio. Se eliminó la copia generada anterior de 228717950 bytes en `apps/gym/dist`, conservando fuentes y licencias.
- Portal compilado: entrada JavaScript de 318,82 kB sin comprimir y 97,61 kB gzip; el cliente Supabase se carga aparte cuando existe configuración. No se midieron Lighthouse ni Web Vitals. El build upstream conserva avisos de chunks grandes; no se presenta como completamente optimizado.
- Worker y setup sin credenciales: terminan con error explícito de configuración, sin llamadas externas ni modificaciones de cuentas.
- `agent-desktop.cmd status` funcionó usando un estado temporal propio. La enumeración nativa de ventanas falló en el usuario sandbox; la comprobación visual e interacción se hizo con Edge mediante Playwright.

## Límites

No se aplicaron migraciones remotas, no se usaron cuentas reales y no se publicó el proyecto. SQL/RLS se probaron en PGlite; el fixture sustituye pgvector por `real[]` y no certifica embeddings. El flujo de nube del navegador usa mocks, no una conexión entre dispositivos reales.

No se inició el contenedor del extractor ni se comprobó OCR de extremo a extremo, Garmin, correo o calendario reales. No se recorrió cada función del openGym upstream. El aspecto sigue siendo provisional. Los datos locales requieren exportación si se limpia el navegador.

La consulta y actualización AST del grafo usó el Python registrado en `graphify-out/.graphify_python`. La herramienta advirtió que no hay parser SQL y que cuatro archivos Gradle upstream tienen análisis parcial; no se instalaron analizadores adicionales para ocultar esas limitaciones.

Documentación consultada: [changelog de Supabase](https://supabase.com/changelog.md), [autenticación con contraseña](https://supabase.com/docs/reference/javascript/auth-signinwithpassword) y [consulta de datos](https://supabase.com/docs/reference/javascript/select). Los informes de los roles se conservaron en el proyecto hermano Agentes, con sus cierres y hashes de evidencia.
